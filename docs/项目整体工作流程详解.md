# WAFByPasser 项目整体工作流程详解

> 本文基于当前仓库实际代码整理，说明项目从启动、录入 Payload、生成候选、真实验证、结果归档到知识库自学习的完整工作流程。

## 一、项目定位

WAFByPasser 是一套面向授权安全测试与防御研究的 WAF Payload 生成、迭代、验证和知识沉淀平台。

它不只是一个编码脚本，而是一条完整闭环：

```text
录入基础 Payload
        ↓
选择迭代方式
  ├─ 语义迭代：改变表达方式，保留攻击目标
  ├─ 编码迭代：施加可逆编码链
  ├─ 穷举迭代：一条原语遍历所有兼容技法
  └─ 正向交叉：语义变体再叠加编码
        ↓
后端确定性校验、重组、去重
        ↓
生成候选并自动进入验证队列
        ↓
发送到配置好的授权靶场
        ↓
根据硬证据判定 WAF 是否放行、攻击是否执行
        ↓
进入 bypass 库 / block 库 / 待人工验证库
        ↓
回写技法成功率、特征统计、转正和淘汰
        ↓
泛化产生下一批 frontier 技法
```

项目的核心原则是：

```text
知识库限定探索空间
→ LLM 提出结构化方案
→ 后端确定性执行和约束
→ 授权靶场提供硬证据
→ 结果反哺知识库
```

## 三、项目启动流程

### 3.1 配置环境

将 `config/.env.example` 复制为 `config/.env`，配置：

- `LLM_BASEURL`
- `LLM_APIKEY`
- `LLM_MODEL`
- `LLM_PROVIDER`
- 可选的独立检验 LLM
- 自动验证开关和并发数
- 授权靶场地址、Host、Cookie 或账号
- 可选 OOB 回连监听地址

默认关键参数：

```text
AUTO_VERIFY=true
VERIFY_CONCURRENCY=3
VERIFY_QUEUE_CAPACITY=5
```

### 3.2 启动后端

```powershell
$env:PYTHONPATH="backend\src"
python -m uvicorn app.main:app --host 127.0.0.1 --port 8000
```

FastAPI lifespan 启动时依次执行：

1. 加载 `.env`。
2. 初始化或迁移 SQLite 数据库。
3. 写入系统内置的知识库分类和基础技法。
4. 将上次异常中断的生成任务标记为失败。
5. 将遗留的验证任务恢复到队列。
6. 启动固定数量的验证 Worker。
7. 服务关闭时停止 Worker。

### 3.3 数据库初始化

数据库默认位于：

```text
data/waf_bypasser.db
```

主要表包括：

| 数据类别 | 主要表 | 用途 |
|---|---|---|
| Payload | `payloads` | 保存基础、归档和池快照 Payload |
| 语义迭代 | `generation_tasks`、`candidates` | 语义任务及候选 |
| 编码迭代 | `encoding_tasks`、`encoding_candidates` | 编码任务及候选 |
| 交叉迭代 | `cross_sources`、`cross_tasks`、`cross_candidates` | 语义结果叠加编码 |
| 验证队列 | `verification_jobs` | 自动检验任务 |
| 结果库 | `bypass_library`、`block_library`、`unverified_library` | 三类互斥结果 |
| 知识库 | `kb_techniques`、`technique_templates` | 技法及模板 |
| 验证历史 | `kb_observations` | 不可变验证观测 |
| 特征统计 | `waf_features` | 危险特征通过率 |
| 学习任务 | `exhaustion_tasks`、`generalization_tasks` | 穷举和泛化 |
| 报告 | `reports`、`report_images` | 报告和证据图片 |

启动时还会幂等写入系统内置语义部件方向，并标记为：

```text
status = seed
origin = system
protected = 1
```

这些是系统基础技法，不能被自动淘汰。

### 3.4 启动前端

```powershell
npm --prefix frontend install
npm --prefix frontend run dev
```

前端运行在 `127.0.0.1:5184`，Vite 将 `/api` 请求代理到 `127.0.0.1:8000`。

## 四、第一步：录入基础 Payload

用户在“Payload 库”中填写：

- 漏洞类型
- 严重程度
- 投递方式
- Payload 内容

前端调用：

```http
POST /api/payloads
```

支持的漏洞类型：

- `command-injection`
- `sql-injection`
- `xss`
- `log4j`
- `file-upload`

后端会验证必填字段和枚举值，并根据内容的 SHA-256 摘要生成内部名称，例如：

```text
Payload · 3a42d9c8e1f0
```

随后写入 `payloads` 表。

### 本步骤结果

得到一条基础“原语”。它是后续迭代、验证、归档和学习的起点。

---

## 五、第二步：进入待迭代池

用户可以将 Payload 加入：

- 语义待迭代池
- 编码待迭代池
- 正向交叉迭代来源

加入语义或编码池时，后端会创建 Payload 快照，而不是让任务直接引用可能继续被修改的原记录。

这样可以保证：

- 修改原 Payload 不影响已排队任务。
- 每轮任务都能追溯精确输入。
- 失败后可以基于同一快照重试。
- 迭代谱系不会因源记录变化而失真。

用户也可以不经过池子，直接创建一次生成任务。

## 六、语义迭代流程

语义迭代支持：

- 命令注入
- SQL 注入
- XSS

入口：

```http
POST /api/semantic-iterations
```

### 6.1 解析 Payload 结构

系统先将完整 Payload 拆成有语义的部件。

命令注入可能被拆成：

```text
安全前缀
引号上下文
命令分隔符
注入命令
参数
管道或条件结构
错误输出处理
```

SQL 注入可能被拆成：

```text
前缀
引号边界
运算符
谓词
比较值
子查询或 UNION
空白结构
注释终止符
```

XSS 可能被拆成：

```text
上下文前缀
标签
属性边界
事件处理器
JavaScript 表达式
闭合结构
```

每个部件记录：

- `part_id`
- `part_type`
- 原始文本 `raw`
- 字符位置
- 是否必选
- 依赖关系
- 解析置信度

如果无法可靠识别结构，接口返回 `422`，不会继续盲目生成。

### 6.2 选择可用技法

系统从 `kb_techniques` 中选择：

- 漏洞类型匹配。
- 属于 semantic 分组。
- 状态不是 `retired`。
- 平台和数据库方言兼容。
- 当前迭代谱系尚未使用。
- 不是已经由部件方向系统单独提供的 `origin=system` 条目。

对于 SQL，系统还会推断原语更接近：

- MySQL
- Oracle
- MSSQL
- PostgreSQL
- SQLite
- generic

明显不兼容的后端专属技法会被剪掉。

技法按历史绕过率排序：

```text
bypass_count / attempt_count
```

有历史数据且成功率高的优先；尚未验证的技法排在已知技法之后。

当前普通语义迭代的目标候选数不是用户输入的固定数字，而是本轮筛选出的知识库技法数量。若无可用技法，任务会以 0 候选完成。

### 6.3 调用 LLM

LLM 收到结构化上下文：

- 基础 Payload
- 漏洞类型和投递方式
- 已解析部件
- 可用方向
- 当前批次知识库技法
- 历史候选预览
- 期望候选数

LLM 必须返回结构化的 `part_operations`，例如：

```json
[
  {
    "operation": "replace",
    "part_id": "p3",
    "part_type": "predicate",
    "value": "新的等价谓词"
  }
]
```

模型负责提出“修改哪个部件、如何修改”，后端负责生成最终文本。

### 6.4 后端执行部件操作

支持三种操作：

- `replace`
- `add`
- `remove`

后端会校验：

- 操作类型是否有效。
- 部件类型是否属于当前漏洞目录。
- 被替换或删除的部件是否存在。
- 是否试图删除必选部件。
- 新增部件 ID 是否以 `new_` 开头。
- 新增依赖是否存在。
- 新增内容是否为空。

### 6.5 确定性重组

后端根据：

- 原始字符位置
- 部件类型
- 依赖锚点
- 语法紧凑规则

重新拼接最终 Payload。它不会简单地在所有部件之间插入空格，因为引号、分隔符、属性和标签边界必须保持紧邻。

### 6.6 候选过滤

候选会经过以下过滤：

- 重组结果为空。
- 以换行符或 `%0a` 开头。
- 与基础 Payload 完全相同。
- 与本轮候选重复。
- 与数据库历史候选重复。
- 仅大小写、空白或标点变化，语义骨架相同。
- SQL 候选缺少真实攻击关键字、运算符、函数或注释。
- SQL 在 URL 路径投递下会被 `#`、`?` 等截断。
- 结果只是无害的验证标记。

### 6.7 保存语义候选

合格候选写入 `candidates`，保存：

- 最终 Payload
- 使用的技法 ID
- 规则标签
- 部件操作
- 变更前后部件
- 语义差异
- 下一步方向
- 解释和置信度
- 可选执行目标和验证规范

### 本步骤结果

得到可追溯的语义候选，而不是只有一组无法解释来源的字符串。

## 七、编码迭代流程

编码迭代支持命令注入、SQL 注入和 XSS。

入口：

```http
POST /api/encoding-iterations
```

### 7.1 LLM 只输出编码意图

编码 Agent 不让模型直接随意生成编码字符串。模型只能声明：

- 单层整句编码
- 单层部分编码
- 最多三层的嵌套编码

例如：

```json
{
  "intent": "nested",
  "chain": [
    {"type": "url", "mode": "partial", "submode": "关键字"},
    {"type": "base64", "mode": "full"}
  ]
}
```

### 7.2 后端实现编码

真正的编码内容由后端确定性计算。项目实现 28 类编码和变形：

| 组 | 编码/变形 |
|---|---|
| URL | URL、全角 URL、IIS `%u`、Jetty `%u` |
| 实体/转义 | HTML 十进制、HTML 十六进制、JS 八进制、JS 十六进制、JS Unicode |
| 进制 | Hex、Binary |
| 算法 | Base64、Base64 Data URI、Quoted Printable |
| 字符集 | UTF-7、CP037、UTF-16BE |
| 结构 | JSON、XML、XML Entity、GraphQL |
| 隐形变形 | 零宽字符、SQL 注释、HTML 注释、空白变形、大小写变形 |
| 压缩/序列化 | Gzip、PHP Serialize |

### 7.3 部分编码模式

部分编码支持：

1. 特殊字符编码
2. 关键字编码
3. 每个 token 首字符编码
4. 关键字内部断点编码
5. 确定性随机比例编码

随机类变形使用稳定种子，因此同一个 Payload、编码名和比例每次运行都会得到相同结果。

### 7.4 场景过滤

系统会根据漏洞场景过滤编码类型。例如 HTML 实体更适合 XSS，而部分字符集或结构编码只对特定上下文开放。

嵌套链中任何一层不适用于当前场景，整条链都应被拒绝。

### 7.5 编码链记录

每条候选保存：

- `encoding_chain`：从内到外的编码步骤。
- `decode_path`：反向解码顺序。
- `segs`：部分编码段的原文位置、长度、编码名和原始子串。

例如：

```text
编码链：部分 URL → 整句 Base64
解码路径：Base64 → URL
```

部分编码必须记录 `segs`，因为系统需要准确知道哪一段被编码，不能对整条字符串做猜测性解码。

### 7.6 可逆性校验

编码模块提供两类硬校验：

1. 从基础 Payload 正向重放编码链，必须精确得到候选。
2. 从候选逆序解码，必须恢复基础 Payload。

零宽字符、注释、空白和大小写变化属于有损表示，逆向后会先执行归一化再比较。

### 7.7 保存编码候选

合格候选写入 `encoding_candidates`，保存：

- 编码后内容
- 编码链
- 解码路径
- 规则标签
- 解释
- 置信度
- 技法 ID

### 本步骤结果

得到可重放、可解码、可追踪技法来源的编码候选。

## 八、正向交叉迭代

正向交叉表示：

```text
基础 Payload
→ 语义变异
→ 语义候选
→ 编码叠加
→ 交叉候选
```

典型流程：

1. 语义候选完成测试。
2. 候选被归档为新的 Payload。
3. 成功语义归档生成 `cross_source`。
4. `cross_source` 自动进入正向交叉池。
5. 编码 Agent 针对语义结果选择编码策略。
6. 后端确定性实现并验证编码链。

每条交叉编码链会计算稳定的 `chain_key`，写入 `cross_chain_history`。

即使用户删除交叉候选，已经使用过的编码链历史仍然保留，下一轮不会重复生成相同链。

### 本步骤结果

得到同时带有语义技法来源和编码链来源的组合候选。

## 九、穷举模式

穷举模式用于尽可能完整地覆盖知识库技法。

入口：

```http
POST /api/exhaustive-iterations
```

### 9.1 执行步骤

1. 读取一条基础原语。
2. 推断漏洞类型和数据库后端。
3. 查询该漏洞类型全部活跃技法。
4. 执行场景剪枝。
5. 执行数据库后端剪枝。
6. 分批调用 LLM。
7. 要求每个技法各生成一条变体。
8. 每条候选精确绑定一个 `technique_id`。
9. 所有候选进入自动验证。

穷举不会因为中途已经出现 HTTP 200 或成功候选就停止。

职责边界：

```text
脚本决定要试哪些技法
LLM 决定怎样将该技法应用到当前原语
真实靶场决定是否真的绕过并执行
```

### 9.2 当前实现边界

当前代码已经执行：

- P1 场景剪枝
- P2 后端剪枝

`version_gate` 版本元数据目前尚未执行完整的 P3 硬剪枝，带版本要求的技法仍会被保留并交给后续流程。

### 本步骤结果

得到“一条原语 × 剪枝后全部技法”的候选集合，以及精确的技法验证统计。

## 十、候选自动进入验证队列

语义、编码和交叉候选落库时，会自动创建 `verification_jobs`。

当 `AUTO_VERIFY=true` 时，状态流转为：

```text
waiting → queued → running → completed / failed
```

| 状态 | 含义 |
|---|---|
| `waiting` | 等待进入有限容量队列 |
| `queued` | 已进入 Worker 可认领队列 |
| `running` | 已被某个 Worker 原子认领 |
| `completed` | 已完成验证和结果同步 |
| `failed` | 网络、解析或内部检验异常 |

Worker 使用 SQLite `BEGIN IMMEDIATE` 原子认领任务，避免多 Worker 重复处理同一个候选。

需要注意：前端提示“生成任务不会向任何目标发包”，准确含义是生成阶段本身不发包。在默认 `AUTO_VERIFY=true` 时，候选生成并落库后会自动进入验证队列，验证 Worker 随后会向 `.env` 中配置的靶场发包。

因此运行完整流程前，必须确认靶场属于明确授权范围。

## 十一、真实靶场验证

项目为不同漏洞提供统一适配器：

- 命令注入：DVWA
- XSS：DVWA，必要时使用 Playwright
- SQL 注入：SQLi-Labs 类靶场
- Log4j：专用靶场
- 文件上传：PHP/JSP Upload-Labs
- 可选 OOB 回连监听

每个适配器返回统一的 `TargetEvidence`：

- 目标标识
- 请求摘要
- HTTP 状态
- 响应头
- 响应正文摘要
- 基线响应
- 最终发送内容
- 请求摘要哈希
- 适配器结果
- 确定性证据

适配器结果分为：

- `waf_blocked`
- `request_error`
- `unsupported_context`
- `application_response`
- `execution_confirmed`

对于需要外带确认的 XSS 或 Log4j Payload：

- 必须配置 OOB 监听器。
- Payload 必须显式包含 `{{OOB_CALLBACK_URL}}`。
- 系统才会将占位符展开为带唯一 token 的回调地址。
- 随后轮询 OOB 服务是否收到回连。

系统不会擅自替换任意外部 URL 或给 Payload 追加外发脚本。

## 十二、最终判定规则

最终成功或失败不由 LLM 决定。

LLM 检验 Agent只补充：

- 分析
- 理由
- 置信度
- 可选路由建议

最终 verdict 由确定性真值表产生：

| 靶场结果 | WAF 判定 | 执行判定 | 结果去向 |
|---|---|---|---|
| WAF 明确拦截 | `block` | `not_confirmed` | block 库 |
| 请求错误或上下文不支持 | `error` | `not_confirmed` | block 库，检验异常 |
| 命中确定性执行证据 | `bypass` | `confirmed` | bypass 库 |
| 应用放行，有验证器但未命中证据 | `bypass` | `not_confirmed` | block 库，验证失败 |
| 应用放行，但无自动验证手段 | `bypass` | `unverified` | 待人工验证库 |

真正进入 bypass 库必须同时满足：

```text
bypass_verdict = bypass
execution_verdict = confirmed
```

仅仅收到 HTTP 200 不足以认定成功。

编码和交叉候选还有一条特殊规则：请求被应用放行后，如果声明的 1～3 层编码链能够逆向恢复基础 Payload，可以作为确定性验证证据。

---

## 十三、验证完成后的事务

每次验证完成，会在同一个数据库事务中执行：

1. 写入不可变 `kb_observations`。
2. 更新候选对应技法的尝试和成功统计。
3. 更新 WAF 特征通过率。
4. 执行技法转正。
5. 执行生成技法淘汰检查。
6. 将候选投影到三个结果库之一。
7. 将 `verification_jobs` 标记为完成。

三个结果库互斥：

### 13.1 bypass 库

条件：

```text
WAF 绕过成功 + 执行验证成功
```

### 13.2 block 库

包含：

- WAF 拦截
- 应用放行但执行未确认
- 请求或检验异常

失败阶段会区分：

- `bypass_failed`
- `verify_failed`
- `check_error`

### 13.3 待人工验证库

条件：

```text
应用已经放行，但当前没有可靠的自动执行确认方式
```

系统在写入一个库前会清理候选在另外两个库中的旧记录，确保同一候选不会同时出现在多个结果库。

---

## 十四、候选归档和继续迭代

完成测试的语义或编码候选可以归档回 Payload 库。

归档记录会保留：

- 来源 Agent
- 来源候选 ID
- 成功或失败结果
- 已使用方向
- 已使用技法 ID
- 迭代谱系
- 下一步方向
- 语义部件或编码链元数据

成功语义候选归档时还会生成 `cross_source`，并自动进入正向交叉迭代池。

因此迭代不是一次性过程，而可以形成：

```text
原始 Payload
→ 第一轮语义变体
→ 归档
→ 第二轮语义变体
→ 正向交叉编码
→ 再次验证
```

---

## 十五、知识库状态机

知识库技法有四个主要状态：

```text
seed → 系统或社区基础技法
frontier → 新生成、尚未证实的技法
promoted → 已至少产生一次真实绕过
retired → 采样充分但从未绕过的生成技法
```

### 15.1 技法转正

验证时会根据候选携带的精确 `technique_id` 回写：

- `attempt_count + 1`
- 绕过时 `bypass_count + 1`
- 绕过时 `success_count + 1`
- 非保护技法在首次绕过后转为 `promoted`

### 15.2 技法淘汰

生成技法同时满足以下条件时会被软淘汰：

```text
protected = 0
不同基础原语采样数 >= 10
bypass_count = 0
origin != community
```

社区主力和系统 seed 永不淘汰。

淘汰是软删除：状态改为 `retired`，并写入技法事件记录，可以保留审计信息。

## 十六、WAF 特征统计

系统会从已验证 Payload 中提取危险特征，例如：

### SQL 注入

- 注释拆分
- 版本注释
- 十六进制字面量
- UNION SELECT
- 延时函数
- 替代空白
- 替代运算符

### 命令注入

- IFS
- 反斜杠拆分
- 引号拆分
- 子 Shell
- 花括号展开
- 通配符
- 替代分隔符

### XSS

- script/svg/img 标签
- 事件处理器
- `javascript:` 协议
- Data URI
- HTML 实体
- JS 执行函数

### 文件上传和 Log4j

- PHP/JSP 扩展名
- 多扩展名
- 魔术字节
- JNDI
- 大小写 lookup
- 嵌套 lookup

每个特征记录：

```text
n_200
n_403
pass_rate = n_200 / (n_200 + n_403)
```

采样达到门槛后：

- `pass_rate >= 0.7`：视为可能的 WAF 盲区。
- `pass_rate <= 0.3`：视为可能的高风险雷区。

这些统计只用于下一轮生成的倾向，不会直接禁用或删除技法。

---

## 十七、泛化产生新技法

语义、编码、交叉或穷举生成成功结束后，系统会自动触发泛化任务。

泛化分为：

- 70% 挖深：根据已有技法、绕过率和 WAF 特征统计探索同族变体。
- 30% 拓新：根据教材文章和模型知识探索新机制。

新技法落库前会经过：

1. 结构字段检查。
2. 编码层、协议层或无效方法预过滤。
3. 机制和族规范化。
4. `(机制, 族, 模板骨架)` L1 签名去重。
5. 必要时注册新的机制和族。

通过后以 `frontier` 状态写入知识库，只有真实绕过后才会转为 `promoted`。

---

## 十八、教材导入

用户在知识库界面导入文章时，系统不会将文章内容直接变成正式技法。

流程是：

1. 计算文章 SHA-256，防止重复导入。
2. 将原文保存到 `data/knowledge_base/notes`。
3. 在 `textbook_notes` 中记录来源和漏洞类型。
4. 后续由拓新 Agent 将其作为燃料。
5. 生成的新技法仍然只能先进入 `frontier`。

这一规则避免“教材中出现过”被误当成“已经在真实 WAF 上验证有效”。

## 十九、前端如何展示任务进度

前端工作区包括：

- 项目仪表盘
- Payload 库
- 语义迭代 Agent
- 编码绕过 Agent
- 正向交叉迭代
- 检验记录
- 靶场管理
- 待人工验证
- bypass 库
- block 库
- 知识库管理

生成任务状态为：

```text
queued → running → completed / failed
```

前端在页面可见时约每 2 秒轮询一次，页面隐藏时约每 5 秒轮询一次。生成期间只轻量刷新候选列表，因此可以看到候选逐批落库，而不必等待全部生成完毕。

## 二十、完整跑完后会得到什么

### 20.1 可追溯候选

包括：

- 候选 Payload
- 来源原语
- 使用技法
- 语义部件操作
- 编码链和解码路径
- 解释与置信度

### 20.2 真实验证证据

包括：

- 靶场目标
- 最终请求摘要
- HTTP 状态
- 响应特征
- 执行证据
- Payload 完整性
- 判定理由

### 20.3 三类结果库

- 绕过且执行成功
- 拦截、执行失败或检验异常
- 需要人工确认

### 20.4 技法效果数据

系统能够知道：

- 每种技法尝试多少次
- 绕过多少次
- 在多少条不同原语上测试过
- 是否应转正或淘汰

### 20.5 WAF 特征画像

系统会逐步积累：

- 哪些危险特征更容易被放行
- 哪些特征更容易被拦截
- 后续生成应优先探索哪些方向

### 20.6 下一轮知识

- 成功技法转为 `promoted`
- 无效生成技法逐步转为 `retired`
- 泛化新技法进入 `frontier`

### 20.7 报告材料

成功样本可以继续整理成验证报告，并上传证据图片。

## 二十一、关键实现边界

### 21.1 LLM 不是最终执行者

- 语义 Agent 输出部件操作。
- 编码 Agent 输出编码意图。
- 检验 Agent 输出辅助分析。
- 后端执行重组、编码、校验和最终真值表。

### 21.2 HTTP 200 不等于成功

只有 WAF 放行且执行获得确定性确认，才会进入 bypass 库。

### 21.3 生成和验证是两个阶段

生成逻辑本身不向目标发送请求；但默认启用自动验证，候选落库后会由验证 Worker 发往配置靶场。

### 21.4 知识库只接受真实验证反馈

教材、新生成技法和 LLM 推断都不能直接证明技法有效。只有真实绕过结果才能推动技法转正。
